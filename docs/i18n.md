# 🌍 Localization (i18n)

[← Back to README](../README.md)

`i18n.NewCatalog` loads application-owned translations from an `io.FS`, such as
an embedded filesystem. Catalogs support go-i18n JSON, TOML, and YAML files and
can be shared by views, workers, and CLI commands.

## Message files

File names identify the language. For example, `locales/active.en.yaml`:

```yaml
page_title: My task list
review.trigger: Trigger
greeting: Hello, {{.Name}}!
tasks:
  one: '{{.PluralCount}} task'
  other: '{{.PluralCount}} tasks'
```

And `locales/active.de.yaml`:

```yaml
page_title: Meine Aufgabenliste
review.trigger: Auslöser
greeting: Hallo, {{.Name}}!
tasks:
  one: '{{.PluralCount}} Aufgabe'
  other: '{{.PluralCount}} Aufgaben'
```

Message IDs are exact keys. The dot in `review.trigger` is part of the key;
it does not describe a nested YAML object. Keep whole messages with named
variables in the catalog so translations can change word order.

## Standalone use

Place the files above in a `locales/` directory next to this Go source file:

```go
package main

import (
    "embed"
    "fmt"
    "log"

    "github.com/alexfalkowski/go-service/v2/i18n"
    "golang.org/x/text/language"
)

//go:embed locales/*.yaml
var assets embed.FS

// NewCatalog loads the application's embedded translations during startup.
func NewCatalog() (*i18n.Catalog, error) {
    return i18n.NewCatalog(language.English, assets, "locales/*.yaml")
}

func main() {
    catalog, err := NewCatalog()
    if err != nil {
        log.Fatal(err)
    }

    localizer := catalog.Localizer("de-CH")
    message, err := localizer.Message("greeting", map[string]string{"Name": "Alex"})
    if err != nil {
        log.Fatal(err)
    }

    fmt.Println(message)
}
```

This prints `Hallo, Alex!`. In a worker, construct the catalog at startup and
select a localizer for each job using the application's language preference.

`Text("review.trigger")` looks up a message without variables.
`Plural("tasks", 2, nil)` selects a CLDR plural form and makes the count
available as `.PluralCount`; the German catalog above produces `2 Aufgaben`.
When supplying non-nil plural data, that data must provide all template variables.
These methods return errors for missing messages, missing variables, invalid
plural counts, or template execution failures; callers should handle them.

## Language selection and lifecycle

`catalog.Localizer(preferences...)` treats each argument as a separate preference
source. A source can be a language tag or an `Accept-Language` value with quality
weights. The first source with a supported match wins; invalid and unsupported
sources are ignored. Regional preferences such as `de-CH` can match `de`.
If no source matches, the catalog's default language is selected.

Missing translations fall back to the default-language message.
`Localizer.Tag()` reports the selected catalog language, even when an individual
message uses that fallback.

Every glob passed to `NewCatalog` must match files, and the default language
must have messages. Unreadable files, malformed catalogs, and message template
syntax errors fail construction. Load catalogs once during startup and share
them across requests or jobs; catalogs and localizers support concurrent use.
There is no runtime mutation or hot reload.

Language preferences, timezones, currencies, and date formatting remain
application policy. Maintain source-catalog entries for keys used in templates:
`goi18n extract` scans Go message definitions, not HTML or Markdown templates.

## Fx wiring

Move the embedded files and `NewCatalog` constructor into an application-owned
package. Register it with `di.Constructor(NewCatalog)` in that package's module,
then compose the module with `module.Server` or `module.Client`:

```go
// Module provides the application's translation catalog.
var Module = di.Module(di.Constructor(NewCatalog))
```

Here `di` is `github.com/alexfalkowski/go-service/v2/di`. Constructors for
workers, commands, or renderers can then receive `*i18n.Catalog` through DI.
The standard module bundles do not supply application translations or choose
their language policy; no shared top-level configuration block is required.

## Markdown rendering

Localizer methods return plain text. Supply the selected `*i18n.Localizer` as
a `Localizer` field on the application's template model and apply the renderer's
escaping rules to translated text and inserted values.

For a `text/template` Markdown renderer, a label can use:

```gotemplate
🔎 **{{ .Localizer.Text "review.trigger" | markdown }}:** {{ .Trigger | markdown }}
```

Here `markdown` is an application-provided Markdown-escaping function registered
in the template's function map. `text/template` does not escape Markdown
automatically. Keep the markup in the template and the translated text in the
catalog.

## HTTP MVC integration

MVC accepts an application-provided catalog and supplies `.Localizer` to its
templates. See [HTTP MVC localization](transport.md#http-mvc-localization) for
view wiring, request language selection, HTML escaping, and response headers.
